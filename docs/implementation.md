# Implementation\n\n## Package\n\nThe package is khmer_ua, with a CLI entry point khmer-ua.\n\n## Data flow\n\nnormalize.py performs Unicode NFC normalization.\n\nparser.py performs conservative orthographic decomposition into consonants, coeng/subscripts, vowel signs and independent vowels.\n\nphonology.py resolves structural register/inherent-vowel metadata without inventing IPA.\n\nipa.py applies pronunciation-profile transformations to already established IPA. It is intentionally not an orthography-to-IPA oracle.\n\npractical.py reads the canonical data/ukrainian/practical-policy.json target policy. map_ipa_string() is the whole-IPA longest-match adapter: it preserves word spaces, removes syllable separators from practical spelling, applies contextual syllable-initial /j/ yotation, and withholds the full practical string if any IPA unit is unsupported.\n\nThe browser's src/ukrainian-practical.js adapter consumes the same canonical Ukrainian policy as the Python layer; src/main.js calls it after source analysis has produced IPA. It must not maintain a second authoritative linguistic table. Regression tests cover /h, ɦ/ → г, /ɡ/ (ASCII /g/) → ґ, /x/ → х, /w, ʋ/ → в, explicit ц/дз/ч/дж affricates, the /cʰ/ → ть' palatal-stop target, yotation and unsupported IPA.\n\n## Determinism\n\nThe implementation is deterministic and dependency-free at runtime. Linguistic uncertainty is represented as status/limitations rather than random or probabilistic output.\n\n## Web build\n\nThe web layer is built with Vite. npm run check performs structural regression checks and npm run build produces the static dist/ artifact used by GitHub Pages.\n\nThe browser service deliberately returns NOT_ESTABLISHED / EVIDENCE_LIMITED for inputs outside the implemented, provenance-bearing examples. This is a correctness boundary: the project must not fabricate IPA.\n\n## API\n\n    from khmer_ua import analyse, render_ipa_profile, map_sequence\n    result = analyse("ខ្មែរ")\n    ipa = render_ipa_profile("krɑː", "khmer-pph-careful-citation-v1")\n    ua = map_sequence(["kʰ", "a"])\n\nThe example IPA is illustrative of the API and must not be read as a claim that the parser currently derives that IPA automatically.\n\n## CLI\n\nkhmer-ua analyse TEXT\nkhmer-ua syllables TEXT\nkhmer-ua ipa TEXT\nkhmer-ua transliterate TEXT\n\nAt present the ipa command prints NOT ESTABLISHED when no IPA engine result exists. Other placeholder commands must not be presented as complete generators.

## Typed phonetic result contract

The browser adapter emits `phonetic_result` using schema identifier `khmer-phonetic-result/v1`. Its unit records keep source text, status, IPA, Ukrainian rendering, profile, provenance and uncertainty aligned. Provenance is separated into structural evidence, pronunciation evidence and target-policy use; Unicode structural support is never presented as phonetic evidence.

Aggregate strings preserve unit order and punctuation. An unresolved unit contributes an explicit local marker rather than replacing the entire input's IPA/Ukrainian output. Consumers must inspect `complete`, `partial`, per-unit `status` and `uncertainty`; concatenated strings alone are not a completeness signal. This follows the typed-result and evidence-lane pattern used in the Lao project while retaining Khmer-specific rules and evidence.

The parser iterates Unicode code points, not UTF-16 code units, and exposes U+ code-point diagnostics for unsupported content. A structurally recognized unit without an IPA source remains NOT_ESTABLISHED. The structural parser and conservative tokenizer do not claim complete Khmer syllable or word segmentation.


The Python `RuleBasedKhmerEngine` uses the same versioned result contract through `khmer_ua.phonetic_result` (`PhoneticResult`, `PhoneticUnitResult`, and `PhoneticUncertainty`). It segments input conservatively, prioritizes exact lexical fixtures, preserves separators, and returns per-unit IPA/UA status and provenance. For mixed input, resolved neighboring units remain visible while unsupported units receive local markers. The Python public API keeps legacy top-level fields for compatibility and adds `phonetic_result`, `complete`, `partial`, and `units`.


The reported `ព្រះរាជាណាចក្រ` false `Unknown character(s)` state has now been traced to the browser parser's unit assumption: the conservative tokenizer can keep several known Khmer base consonants in one orthographic chunk, but the parser previously treated every post-base consonant outside a COENG pair as unknown. The parser now records every recognized consonant as a consonant grapheme and withholds phonetic output when the chunk cannot be confidently syllabified. This is a structural-recognition correction, not a new pronunciation rule; the absence of a lexical IPA fixture still yields NOT_ESTABLISHED.
